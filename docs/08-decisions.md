# GridProof — Decisions

**Document:** `docs/08-decisions.md`  
**Version:** 1.0 · 2026-10-17  
**Purpose:** Short record of decisions that guide implementation. Sources are cited. New decisions are added; superseded ones are marked, not deleted.

## Product and architecture (already in the specifications)

| ID | Decision | Source |
|---|---|---|
| D-01 | Independent, Cummins-inspired product. Not affiliated. All operational data is synthetic. Fridley is the only interactive lab. | CLAUDE.md, docs 01, 10 |
| D-02 | Modular-monolith FastAPI backend. No microservices, queues, Redis, Kafka, AWS or Kubernetes without a demonstrated requirement. | CLAUDE.md, doc 03 |
| D-03 | Deployment: Vercel (frontend), Render (backend), Neon (PostgreSQL). | CLAUDE.md, doc 03 |
| D-04 | Anonymous cookie workspaces with a fixed 7-day expiry from creation. Only the token hash is stored. | docs 03, 04, 05 |
| D-05 | Configuration versions and completed run evidence are immutable (append-only). | CLAUDE.md, doc 04 |
| D-06 | The simulator is a pure, deterministic Python module run synchronously in the API. Gemini is optional and drafts tests only. | CLAUDE.md, doc 03 |
| D-07 | PDF evidence is generated from a saved run and never re-runs the simulation. | docs 02, 10 |

## Decisions made on 2026-10-17 (project owner)

| ID | Decision |
|---|---|
| D-08 | **Session initialization is atomic.** `GET /api/v1/session` is exposed only when it creates the workspace, the default Fridley configuration and configuration version 1 in one transaction, rolling back on any failure. No interim workspace-only endpoint. Roadmap tasks: A-02 (`SystemConfigV1`), A-03 (atomic service), A-04 (endpoint). |
| D-09 | **F-11 precedes database-backed work.** Isolated PostgreSQL integration testing is a prerequisite for database-backed session and configuration features. Automated integration tests never run against production Neon. |
| D-10 | **The API contract is preserved.** The current `/health` response (`status`, `service`) does not match doc 05 API-01 (also `version`, `model_version`). The mismatch is an outstanding implementation issue (task C-11); the specification is not weakened. |
| D-11 | **Dependencies named in doc 03 are conditionally approved** (shadcn/ui, TanStack Query, Recharts, ReportLab, Playwright, Hypothesis, httpx) when the feature that needs them is implemented. Major new dependencies still require justification and approval. |
| D-12 | **PDF export** has implementation priority P1 but is required for the finished showcase. HTML-only export does not satisfy acceptance criteria. |
| D-13 | `CLAUDE.md` is a local instruction file and is ignored through `.git/info/exclude`, not the repository `.gitignore`. |
| D-14 | Document versions and dates change only when content changes substantively. Completed roadmap tasks are not reset. |
| D-15 | **Automated database tests use isolated PostgreSQL.** Locally: a Docker container (`backend/docker-compose.test.yml`, loopback port 55432, `tmpfs` data). In GitHub Actions: a PostgreSQL service container. `TEST_DATABASE_URL` must be the approved disposable instance (host `127.0.0.1`/`localhost`, port 55432 or 5432, database `gridproof_test`, role `gridproof`); `backend/tests/integration/db_safety.py` rejects anything else, including all Neon hosts, before an engine is created. Integration tests never read `DATABASE_URL`. Migrations run in tests through an injected connection (`config.attributes["connection"]` in `migrations/env.py`), which leaves production migration behavior unchanged. In CI a missing test database fails the build (`GRIDPROOF_REQUIRE_TEST_DB=1`) instead of skipping. Production Neon is never used for automated tests. |
| D-16 | **Facility catalog seed (A-01).** The three rows are written by an idempotent upsert module and CLI (`python -m app.seed.facilities`), not by an Alembic migration (no migration renumbering). The CLI is a dry run unless `--apply` is given; a non-loopback database additionally requires `--confirm-host <exact host>`; connection URLs and passwords are never printed. Running it against Neon needs separate approval. Business purposes come from Cummins' own pages; map positions are **approximate city locations** (Wikipedia city entries) and every `source_note` says so. Only Fridley is interactive. No equipment lists, metrics or operating conditions are stored. `GET /api/v1/facilities` is a separate task (A-01b). |
| D-17 | **Facility endpoint (A-01b).** `GET /api/v1/facilities` is public and read-only and returns the documented catalog fields plus the additive `description` (doc 05 v1.1). `200` carries `Cache-Control: public, max-age=300`; every error response carries `Cache-Control: no-store` and a generated `X-Request-ID` equal to `error.request_id`. A database failure or an empty catalog returns `503 CATALOG_UNAVAILABLE`; any other failure inside the route returns `500 INTERNAL_ERROR`. Error handling is **scoped to this route**: there is deliberately no application-wide exception handler. Request IDs are generated, not accepted from the client. |
| D-18 | **SystemConfigV1 (A-02).** The schema lives in `app/domain/system_config.py` as frozen, `extra="forbid"` Pydantic models with no mutable containers. `battery.min_soc_pct` (20) and `utility.available` (true) are fixed in V1, alongside facility, ratings, sizes, `switchgear.mode` and the equipment id set. Editable values are strict integers (`startup_delay_s` 0..120, `initial_soc_pct` 0..100 and at least the minimum, `critical_kw` 1..500) and a strict boolean (`enabled`); booleans, decimals, strings and non-finite numbers are rejected. `load.critical_kw` is the baseline load; `set_load_kw` scenario events change demand during a run and the load-bank view shows simulated demand, so no load-bank field exists in V1. Validation errors become `{field, reason}` details with stable messages and a safe generic fallback; submitted values are never echoed. `ConfigurationName` (trimmed, 1..100 characters, no control characters, one visible character) closes the tab/newline gap left by the database check. Stored snapshots are loaded with `load_snapshot(schema_version, data)`, which rejects any version other than `config-v1`. |
| D-19 | **Workspace initialization (A-03).** `initialize_workspace(session)` in `app/services/workspaces.py` creates the workspace, the default Fridley configuration (name "Fridley Test Configuration") and immutable version 1 as one unit. **The caller owns an active outer transaction**: the service rejects a session without one (`TransactionRequiredError`), never commits, and never rolls back the caller's transaction; all of its work runs in a savepoint so a failure removes only its own rows. The session token is `secrets.token_urlsafe(32)` (256 bits); only its SHA-256 hex digest is stored (no pepper or new secret, by owner decision); the plaintext is returned once in `NewWorkspace` (hidden from `repr`) and is never logged. `expires_at` is `now() + 7 days` computed by PostgreSQL in the same transaction as `created_at`. The configuration pointer moves to 1 only after version 1 exists. A missing `fridley` catalog row raises `CatalogNotSeededError`. |
| D-20 | **Session endpoint and issuance cap (A-04).** `GET /api/v1/session` (`app/routes/session.py`, `app/services/sessions.py`) reuses a valid workspace without renewing the fixed expiry and without taking any lock; otherwise it issues a new one. Issuance runs in one transaction: `SET LOCAL` lock/statement timeouts (2 s / 5 s), `pg_advisory_xact_lock`, a count of workspaces with `created_at` in the last 60 s (cap 120, global, not per-IP: no trustworthy client address behind Vercel/Render), `initialize_workspace`, commit. The cookie is set only after the commit. Cookie: `gridproof_demo`, `HttpOnly; Secure; SameSite=Lax; Path=/`, host-only, `Max-Age` = remaining lifetime. All responses carry `Cache-Control: no-store` and `Vary: Cookie`. Malformed, unknown, expired or duplicated cookies mean "no session". Lock wait timeout and an unseeded catalog are `503 DATABASE_UNAVAILABLE` (logged as `lock_timeout`, with `Retry-After: 5`, and `catalog_not_seeded`); the cap is `429 SESSION_RATE_LIMITED` with `Retry-After: 60`. `created_at` is counted directly (no index; acceptable at this scale). GET session creation is a documented exception; no frontend prefetching. Doc 05 is v1.3. |
| D-21 | **Current configuration (A-05).** `GET /api/v1/configurations/current` resolves the workspace only from the session cookie, reusing the A-04 cookie parser and A-03 token hash (`app/services/workspace_auth.py`), and is read-only: it never creates or renews a workspace and never sets a cookie. `SESSION_REQUIRED` (401) covers a missing, malformed, duplicated or unknown token; `WORKSPACE_EXPIRED` (401) a well-formed token matching an existing expired workspace. The configuration is selected by workspace only (no facility condition; latest `updated_at`, then id), and the version named by `latest_version` is read in the same statement. The snapshot goes through `load_snapshot(schema_version, data)` and the normalized snapshot is returned. An unsupported schema version, invalid snapshot, or a pointer that is 0 or names a missing version is `500 INTERNAL_ERROR` (logged as a reason code with the configuration id, never with data); no configuration is `404 CONFIGURATION_NOT_FOUND`. Nothing is repaired or modified. All responses carry `no-store` and `Vary: Cookie`. Doc 05 is v1.4. |
| D-22 | **Version saving (A-06).** `POST /api/v1/configurations/{id}/versions` runs one transaction: workspace-scoped `SELECT ... FOR UPDATE` on the configuration (transaction-local 2 s lock and 5 s statement timeouts; a lock timeout is `503` with `Retry-After: 5`), validation of the stored latest version through its recorded schema version, `expected_version` comparison, version insert (`latest_version + 1` from the locked row), and the name and pointer update, committed before the success response. A missing or foreign id is the same `404`. Stale submissions are `409` with `details: [{field: current_version, reason: n}]`. **Best-effort replay:** when `expected_version + 1 == latest_version` and the name and validated snapshot equal the stored ones, `200` returns the existing version and creates nothing; this is content matching, not request idempotency, and no idempotency table was added. The name lives on the configuration row and is not versioned. A pointer of 0, a missing pointer target or an invalid stored snapshot is `500` and a save never repairs it (`expected_version = 0` is accepted syntactically only). Write requests check `Origin` against the optional `FRONTEND_ORIGINS` setting (comma-separated; empty rejects every browser origin; absent `Origin` is accepted). Bodies over 256 KiB (actual bytes) are `413`; malformed JSON, duplicate keys, non-finite numbers and invalid fields are sanitized `422`. Doc 05 is v1.5. |
| D-23 | **Startup-check demo endpoint (conference scope).** `POST /api/v1/demo/startup-check` is a stateless, read-only, workspace-scoped computation over an immutable saved configuration version, backed by the pure model in `app/domain/startup_check.py`. It persists no run, adds no migration and no dependency, and is not the planned API-10 run. Decisions fixed by the project owner: only G1 is commanded (G2 is not, even when enabled); available battery energy is `usable_kwh × (initial_soc_pct − min_soc_pct) / 100` with no conversion losses; outage detection and generator transfer are both 0 ms with readiness and transfer as separate events; the horizon is 300 s; time and energy are accumulated as exact integers and only displayed metrics are rounded; requirements use unrounded values. The Origin allowlist check moved unchanged to `app/core/origin.py` and is shared with API-06. |
| D-24 | **Daventry exercise amendment (2026-10-19, owner-approved).** FR-03, AC-02 and AC-UF01-04 are amended to permit, once implemented and verified, a clearly labeled independent synthetic generator-package screening exercise at Daventry, with no real factory operations or official Cummins product selection claims. Backend validation is the preferred approach for its deterministic capacity check; the endpoint is **not** implemented and no API contract changed. Neon seed records and facility descriptions stay unchanged until the workbench is implemented and independently verified. Seymour's engine test-plan exercise and the mining/on-highway ideas remain post-SHPE roadmap concepts only. |
| D-25 | **Guided challenges reuse existing state (2026-10-19).** No new endpoint, schema, simulator or state framework. A pure function (`deriveChallenge.ts`) reads the draft, the latest saved version and live evidence; progress never comes from clicks. A fresh result is live, for this workspace's configuration id and latest version. Presets edit only the field their button names and only the draft; they never enable G1 or save. A prediction is stored as configuration id + version + the result sequence number at prediction time (`ComparisonResult.seq`, added to `useStartupComparison`; it advances only when a live run completes and is applied, never for failed, superseded, cleared or recorded results), so a qualifying run is one that finished later and matches the predicted configuration id and version, not an object-identity match. The frontend never recomputes energy or pass/fail. |
| D-26 | **Observation memory for G1 repair (2026-10-19).** After a repair the saved version no longer fails, so the panel remembers the fresh failure it observed (per configuration id) to show the earlier steps as done. This is derived from evidence, not a click, but it is in-memory only and lost on reload. |
| D-27 | **Daventry workbench design (2026-10-19, owner-approved plan).** (1) `is_interactive` keeps meaning "has the Fridley lab"; Daventry's entry comes from a frontend experience registry keyed by facility id, so the seed, Neon rows and catalog descriptions are unchanged (the card shows the factual description under "About the real site" and the workbench in a separate labeled box). (2) `POST /api/v1/demo/capacity-check` (API-17) is a pure, stateless, session-free computation with the API-16 request conventions; it works without a cookie or a database. (3) Exact `Fraction`/`Decimal` arithmetic and exact decimal parsing of the request: 228 kW at 0.57 pf is exactly 400 kVA, which float division reports as 400.00000000000006. (4) Four fixed synthetic packages (200/250, 320/400, 480/600, 640/800 kW/kVA, rated at 0.8 pf, none equal to Fridley's 250 kW); two requirements judged separately per package; no score, ranking or recommendation. (5) The route reuses the request helpers of `routes/demo.py` without modifying that file, and shares only `RuleError` and `validation_details` with `system_config.py`. (6) The map click on Daventry selects it and shows the card; the workbench opens from the card's button. |
| D-28 | **Mining duty-cycle analyzer (2026-10-20, owner-approved plan; moves H-12 forward in part).** (1) The analyzer opens from the Mining and off-highway Industry Applications brief by the hash route `#mining-duty-cycle`, the same pattern as Daventry's `#daventry-workbench`; it is not a map facility and adds no catalog row, seed or `is_interactive` change. (2) `POST /api/v1/demo/duty-cycle` (API-18) is pure, stateless and session-free with the API-16/17 request conventions. (3) Amendments: the application briefs were documented as informational context only, and the PRD excluded mining modules; both now permit this one clearly labeled, independent, synthetic calculator that works only on numbers the user enters. It is not a simulated facility, a mining module, a vehicle simulator or real Cummins operations; every sample value is invented. (4) Exact `Fraction` arithmetic for every engineering value and for dominance (equal energies tie and are all reported); only serialized values are rounded, half up, to 2 decimals, and the UI says rounded shares can differ slightly from 100%. (5) The modeled shift may not exceed 1,440 minutes (cycle duration x cycles per shift), reported as a field error on `cycles_per_shift`; power is non-negative. (6) The analyzer makes no claim about fuel use, range, propulsion or validated haul-truck performance. (7) Reuse: `Field` moved unchanged to `components/workbench/Field.tsx`; a generic `useStatelessCheck` hook is new and `useCapacityCheck` is untouched; the route reuses the request helpers of `routes/demo.py`. (8) Release note: the Render backend did not auto-deploy API-17 promptly (see PROJECT-STATUS), so the endpoint must be live before the frontend that calls it is released. |
| D-29 | **Mobile-Site Power Planner (2026-10-26, owner-approved plan H-12b).** (1) Use case: a temporary mobile-powered site supplied by an illustrative trailer-mounted source; the model covers the site's electrical demand, not the truck or trailer (a truck-mounted or trailer-focused framing was rejected because it would need vehicle or equipment data). (2) It opens from the On-highway trucks and mobile power brief by the hash route `#mobile-power-planner`; it is not a map facility and adds no catalog row, seed or `is_interactive` change. (3) `POST /api/v1/demo/mobile-power` (API-19, `mobile-power-v1`) is pure, stateless and session-free with the API-16 to 18 request conventions. (4) Amendments: the on-highway brief was informational and the PRD excluded trucking modules; both now permit this one clearly labeled, independent, synthetic calculator over user-entered loads; it is not a simulated facility, a vehicle model or real Cummins operations. (5) Exact `Fraction` arithmetic for every value and verdict; only serialized values are rounded, half up, to 2 decimals, so a requirement that displays equal to a rating can still fail. (6) Four invented packages at 30, 60, 100 and 150 kW (M1 to M4), kW only; no recommendation, ranking or product selection. The modeled-demand requirement is compared with an all-simultaneous sensitivity (every load at 1.00) and each package gets one of three neutral categories. (7) Bounds: 1 to 12 loads, quantity 1 to 100, rated kW above 0 to 500, simultaneity 0.01 to 1.00, margin 0 to 50, total connected load at most 2,000 kW; they are exercise bounds, not engineering limits. (8) The UI states visibly that simultaneity factors are planning assumptions and that only steady-state kW is screened. (9) Reuse: `useStatelessCheck` and `Field` unchanged; the route reuses the request helpers of `routes/demo.py`; the domain module shares only `RuleError` and `validation_details` with `system_config.py`. (10) Release order as for D-28: backend live and verified before the frontend that calls it. |
| D-30 | **Seymour Engine Test-Plan Workbench (2026-10-26, owner-approved plan H-11 with four refinements).** (1) A clearly synthetic, independent engine test-planning exercise opened from the Seymour card by `#seymour-test-plan`; Seymour stays a catalog row with `is_interactive = false`, the seed and the real-site description are unchanged, and it is not the site's software, procedures or data. (2) `POST /api/v1/demo/engine-test-plan` (API-20, `engine-test-plan-v1`) is pure, stateless and session-free with the API-16 to 19 conventions. (3) Coverage is not acceptance: statuses are Covered by plan, Partly covered, Not covered; the response carries a constant `verification.status = "not_verified"`; no pass, verified or performance status is ever shown, and a matching point does not show an engine can operate there. (4) `min_points` counts planned entries; repeated speed/torque coordinates are allowed, count separately, are never deduplicated, and the distinct-condition count is disclosed. (5) Dwell is planned hold, not measured stabilization; the summary is Planned hold time (scheduled holds only), not total elapsed test time; transition, setup and stabilization time are not modeled. (6) Theoretical shaft power = 2 x pi x rpm x N·m / 60,000 in 80-digit `Decimal` arithmetic from a 50-decimal pi (a rounded 9549.3 divisor was rejected); every coverage and threshold comparison uses unrounded values before 2-decimal half-up display. (7) Requirement = speed and torque rectangle (inclusive) plus optional minimum theoretical power, minimum planned entries and minimum planned hold. (8) Bounds (exercise bounds, not engine limits): rpm 1..6,000 whole; torque 0..20,000.00 N·m; dwell 1..480 min; total hold at most 1,440 min; 10 requirements; 12 points. (9) The speed-torque diagram draws only requirement rectangles and planned points: no iso-power curves, performance curve, limit or envelope. (10) The evidence checklist is generic, read-only, starts every item Not started and cites no standard or company procedure. (11) Amendments: the PRD, flows and architecture no longer describe Seymour as informational only; Daventry, Mining, Mobile Power and Fridley are unchanged. (12) Excluded: test-data ingestion, engine operating envelope, fuel, efficiency, emissions and sequencing optimization. |
