# GridProof — Testing Strategy

**Document:** `docs/07-testing-strategy.md`  
**Version:** 1.0 · 2026-10-17  
**Scope:** What exists, how it is run, and what is not yet covered. Only observed results are recorded.

## Principles

- Passing code is not correctness; every feature must satisfy its acceptance criteria in doc 02.
- Test normal inputs, invalid inputs, boundaries and failures.
- Expected values are determined independently of the code under test.
- Never fabricate results, metrics or verification claims.
- **Integration tests never run against production Neon.** They use an isolated PostgreSQL instance (task F-11).
- CI must remain green.

## Commands

| Area | Commands (run from `backend/` or `frontend/`) |
|---|---|
| Backend | `python -m ruff format --check app tests migrations/env.py`, `python -m ruff check app tests migrations/env.py`, `python -m pytest -q` (the autogenerated migration revisions in `migrations/versions/` are intentionally not reformatted) |
| Frontend | `npm run format:check`, `npm run lint`, `npm run typecheck`, `npm run test`, `npm run build` |

CI (`.github/workflows/ci.yml`) runs both sets on push and pull requests to `main`. The frontend job installs with `npm install` (restoring `npm ci` is F-10/G-02). The backend job keeps a dummy `DATABASE_URL` (the app is imported but never connects) and adds a PostgreSQL 17 service container for the integration tests (`TEST_DATABASE_URL`, `GRIDPROOF_REQUIRE_TEST_DB=1`). The first run (GitHub Actions run 39096658114, commit `2041663`) passed both jobs.

## Integration tests (F-11)

Location: `backend/tests/integration/`. They run only against the disposable PostgreSQL described in decision D-15 and never read `DATABASE_URL`.

```
docker compose -f backend/docker-compose.test.yml up -d --wait
$env:TEST_DATABASE_URL = "postgresql://gridproof:gridproof_test@127.0.0.1:55432/gridproof_test"
cd backend; python -m pytest -q
docker compose -f backend/docker-compose.test.yml down -v
```

| `test_facility_seed.py` | A-01 seed on real PostgreSQL: exact rows, only Fridley interactive, idempotency, drift repair, unexpected-row abort, foreign-key compatibility, CLI dry run (no connection), `--apply`, remote-host refusal, credential-safe errors, rollback after a failure past the upsert. |
| `test_transactions.py` | Multi-table rollback on exception and on a database error; commit visibility between connections; row lock blocking (`SELECT ... FOR UPDATE`); concurrent duplicate version. Waits are bounded by `lock_timeout`. |

Isolation: constraint tests run in a rolled-back outer transaction; transaction tests commit and then `TRUNCATE` the four tables; migration tests reset the `public` schema first; each module re-migrates. Results do not depend on test order.

Behavior without a database: locally the integration tests skip with a message; with `GRIDPROOF_REQUIRE_TEST_DB=1` (CI) they error.

Configuration schema without a database: `backend/tests/test_system_config.py` and `backend/tests/test_configuration_name.py` (242 tests, including the explicit `load_snapshot` schema-version loader) check the default against an independent copy of the doc 05 example, accepted boundary edits, every rejection with its exact field path and reason (all integer fields against booleans, floats, strings, `None`, NaN and infinity; fixed values; unknown, missing and misspelled equipment), JSON input, error details that never echo input, immutability at every level, absence of mutable containers, and the name rules.

Endpoint behavior without a database: `backend/tests/test_facilities_endpoint.py` (13 tests, mocked session) covers the response shape, database failure, empty catalog, unexpected error and corrupt row, secret-free responses and logs, `no-store` and request-id headers, no application-wide exception handler, read-only methods, and unchanged health routes.

Seed data rules (no database): `backend/tests/test_facility_seed_data.py` checks the three rows against independently written expectations and rejects invalid rows and catalogs.

## Gaps

- Integration tests exist for the schema only. There is no application code to test yet (workspaces, seeding, configuration service).
- `ApiStatus` has no test.
- No tests for workspaces, seeding, configuration schema or versioning (A-01 onward).
- No determinism, golden-fixture or invariant tests for the simulator (C-10).
- No end-to-end browser tests (E-06).

## Planned approach

1. **F-11:** implemented (see above). CI confirmation is pending.
2. **Database-backed features:** transactional tests including injected failures and rollback (A-03), cross-workspace isolation, expiry, conflict handling (A-06).
3. **Simulator:** golden fixtures (5 s pass / 15 s fail), repeat-run determinism, conservation of power, negative and boundary input tests.
4. **Release:** Playwright flagship walkthrough against an isolated test database.
